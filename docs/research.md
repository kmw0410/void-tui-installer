# Research and implementation decisions

## Searchable repository packages (2026-10-19)

The [official xbps-query manual](https://man.voidlinux.org/xbps-query.1) documents `--repository`, `-i` (ignore configured repositories), wildcard `-s` search over pkgver/short_desc, `pkgname` and the memory-only `-M` option. Repository browsing uses the existing XBPS toolchain and Live signing keys in a private metadata root. Additional selection accepts exact package names; installed-state markers in search output do not affect target selection. A read-only `xbps-query -M -i --repository=https://repo-default.voidlinux.org/current -s '*'` query returned 14,823 records, including `[-]` and `[*]` state markers; both formats were parsed by the Go snapshot test. This query did not install packages or update the host package database. Runtime helper execution on an official Live ISO remains a separate integration check.

## Timezones and niri usability (0.4.0-dev)

The searchable timezone allowlist is bundled from the public-domain [IANA zone.tab](https://github.com/eggert/tz/blob/main/zone.tab), retrieved 2026-10-15, plus UTC. The installed tzdata file is linked from `/etc/localtime`, following [Void date/time configuration](https://docs.voidlinux.org/config/date-time.html). No time synchronization service is added.

Niri's [built-in Xwayland integration](https://niri-wm.github.io/niri/Configuration%3A-Miscellaneous.html#xwayland-satellite) manages the bridge on demand; the [Void xwayland-satellite package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/xwayland-satellite/template) depends on xorg-server-xwayland. The [packaged polkit agent entry](https://github.com/void-linux/void-packages/blob/master/srcpkgs/polkit-gnome/files/polkit-gnome-authentication-agent-1.desktop) confirms `/usr/libexec/polkit-gnome-authentication-agent-1`; niri starts it explicitly because the upstream systemd autostart integration is not used. [Void NetworkManager guidance](https://docs.voidlinux.org/config/network/networkmanager.html) requires D-Bus, network-group membership and disabling competing network services. The [network-manager-applet package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/network-manager-applet/template) provides the connection editor; its tray applet is left to user configuration. Both desktops initialize standard user directories with xdg-user-dirs; niri includes pavucontrol. Package availability is also checked by the normal signed XBPS transaction preflight before erasure.

Research date: 2026-10-15. Runtime is the official Void Linux x86_64 glibc Live ISO, booted in UEFI mode. The development host only compiles the binary, runs non-destructive checks, and hosts isolated virtual machines. A non-Void development host is not a supported installation runtime.

## Optional desktops, graphics and input methods

The expanded graphical profiles use Void's `libjack-pipewire` package name, not Arch's `pipewire-jack`. `alsa-pipewire` routes ALSA clients; packaged `10-wireplumber.conf` and `20-pipewire-pulse.conf` fragments let one user PipeWire instance launch its session manager and PulseAudio compatibility server. KDE uses XDG autostart and niri uses compositor startup. JACK library precedence follows Void's documented ldconfig method. KDE also installs Bluetooth audio plugins. Sources: [PipeWire handbook](https://docs.voidlinux.org/config/media/pipewire.html), [Void PipeWire package/subpackages](https://github.com/void-linux/void-packages/blob/master/srcpkgs/pipewire/template).

Niri now includes GNOME and GTK portal backends, GNOME Keyring and Seahorse. GNOME's default file chooser requires Nautilus, so the per-user niri portal preference explicitly selects GTK for FileChooser and GNOME Keyring for Secret. Niri exports display/session variables into D-Bus activation after the compositor starts; systemd user services are not used. SDDM PAM hooks provide optional login unlocking for GNOME Keyring or KWallet while preserving normal authentication. Sources: [niri important software](https://niri-wm.github.io/niri/Important-Software.html), [Void GNOME portal dependencies](https://github.com/void-linux/void-packages/blob/master/srcpkgs/xdg-desktop-portal-gnome/template), [GNOME Keyring package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/gnome-keyring/template), [Seahorse package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/seahorse/template), [upstream SDDM PAM configuration](https://github.com/sddm/sddm/blob/v0.21.0/services/sddm.pam).

Mirror selection must happen before repository preflight. Void's published directory lists Fastly CDN and Korean/Japanese Tier 2 mirrors; Tier 2 completeness/freshness is not guaranteed. Mirror roots have different deployment paths, so `/voidlinux` must not be appended unconditionally. The root supplied by the user is preserved and repository suffixes are derived. Installed settings override packaged repository files using identical basenames under `/etc/xbps.d`, including nonfree when selected. Sources: [published mirrors](https://xmirror.voidlinux.org/), [Void mirror configuration](https://docs.voidlinux.org/xbps/repositories/mirrors/changing.html).

The minimal Plasma profile selects `plasma-desktop` and `plasma-workspace` directly; the full `kde-plasma` metapackage brings additional applications. Both desktop choices use SDDM, as explicitly approved after research found no Void `plasma-login-manager` package and upstream requires systemd/libsystemd. SDDM's packaged runit service activates elogind and waits for D-Bus. Sources: [Plasma desktop package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/plasma-desktop/template), [full Plasma metapackage](https://github.com/void-linux/void-packages/blob/master/srcpkgs/kde-plasma/template), [Plasma Login Manager build requirements](https://github.com/KDE/plasma-login-manager/blob/master/CMakeLists.txt), [SDDM runit service](https://github.com/void-linux/void-packages/blob/master/srcpkgs/sddm/files/sddm/run).

Void packages niri without systemd integration. Its packaged session entry refers to `niri-session`, whose upstream launcher only handles systemd or dinit. The installer replaces that entry with a local `dbus-run-session niri --session` launcher using elogind. It does not add application launchers, a bar, Firefox or Kitty unless selected. Sources: [Void niri package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/niri/template), [upstream launcher](https://github.com/niri-wm/niri/blob/main/resources/niri-session), [Void seat management](https://docs.voidlinux.org/config/session-management.html).

Plasma's NetworkManager applet needs the actual NetworkManager service and membership in the `network` group. dhcpcd and other competing interface managers must be disabled. Static configuration uses a MAC-bound NetworkManager keyfile; DHCP uses the internal DHCP client. Source: [Void NetworkManager](https://docs.voidlinux.org/config/network/networkmanager.html).

Void provides `fcitx5-hangul` and separates Qt/GTK input modules from their common packages: `fcitx5-qt5`, `fcitx5-qt6`, `fcitx5-gtk+3`, and `fcitx5-gtk4`. All appear under their actual names in Utilities. KWin launches Fcitx as its Wayland input method; niri uses explicit startup and QT_IM_MODULE. GTK_IM_MODULE is not forced globally, preserving native Wayland text-input. Sources: [Hangul package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/fcitx5-hangul/template), [Qt subpackages](https://github.com/void-linux/void-packages/blob/master/srcpkgs/fcitx5-qt/template), [GTK subpackages](https://github.com/void-linux/void-packages/blob/master/srcpkgs/fcitx5-gtk/template), [Fcitx Wayland setup](https://fcitx-im.org/wiki/Using_Fcitx_5_on_Wayland/en).

Void's current `nvidia` package uses open kernel modules and supports Turing or newer; older families require separate legacy packages. Rather than infer architecture from broad PCI ranges, the installer checks each detected PCI/subsystem identity against NVIDIA's current-products table for the exact version resolved by XBPS. Legacy sections are explicitly excluded. Only the mainline package is offered, with default kernel/Mesa drivers available for unsupported hardware. Sources: [Void NVIDIA handbook](https://docs.voidlinux.org/config/graphical-session/graphics-drivers/nvidia.html), [Void NVIDIA package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/nvidia/template), [NVIDIA 595.104.02 support table](https://download.nvidia.com/XFree86/Linux-x86_64/595.104.02/README/supportedchips.html).

## Bubble Tea v2

The official latest-release API returned Bubble Tea **v2.1.0**, Lip Gloss **v2.0.6**, and Bubbles **v2.2.1**. Their module paths are `charm.land/bubbletea/v2`, `charm.land/lipgloss/v2`, and `charm.land/bubbles/v2`. Use v2 `tea.View`, its alternate-screen setting, `tea.KeyPressMsg`, and `tea.WindowSizeMsg`; avoid v1 API examples. Long operations are commands/messages and external-process readers, never work inside the update loop. Password inputs use masked echoes. The installer keeps the program running while the child process terminates and is reaped.

Sources: [Bubble Tea releases](https://github.com/charmbracelet/bubbletea/releases/tag/v2.1.0), [Lip Gloss releases](https://github.com/charmbracelet/lipgloss/releases/tag/v2.0.6), [Bubbles releases](https://github.com/charmbracelet/bubbles/releases/tag/v2.2.1), [Bubble Tea source](https://github.com/charmbracelet/bubbletea).

Actual Linux VT testing exposed legacy F2 decoding: the terminal sends `ESC [[ B`, but the pinned Ultraviolet decoder emits an unknown CSI and a letter. The project supplies a Linux-only event filter for the legacy F1–F5 suffix, with a regression test using the actual decoder. Upstream has open fixes for the same encoding: [Ultraviolet PR 159](https://github.com/charmbracelet/ultraviolet/pull/159), [PR 136](https://github.com/charmbracelet/ultraviolet/pull/136). This avoids changing the user's console keymap or mixing Bubble Tea API versions.

## Installation and boot

The [official chroot guide](https://docs.voidlinux.org/installation/guides/chroot.html) defines the XBPS bootstrap, copying trusted repository keys, mounting an ESP at `/boot/efi`, installing `grub-x86_64-efi`, and final `xbps-reconfigure -fa`. The installer fixes the target architecture to x86_64 glibc and uses the official HTTPS current repository. Package source existence does not prove binary availability: the engine must resolve every required package against live repository metadata before erasing the disk.

The ESP is 1 GiB FAT32, the rest Btrfs. Btrfs mount points use filesystem UUID plus explicit `subvol=`. `/boot` remains inside `@`; GRUB and kernel command-line configuration must agree on `subvol=@`. The handbook documents `--no-nvram` when EFI variables are unavailable and `--removable` for the UEFI fallback path. Existence of the resulting EFI executable, kernel, initramfs, and GRUB configuration is required; a failed NVRAM write alone must never imply success.

Sources: [chroot guide, including GRUB troubleshooting](https://docs.voidlinux.org/installation/guides/chroot.html), [Btrfs mount options](https://btrfs.readthedocs.io/en/latest/btrfs-man5.html), [base-system package dependencies](https://github.com/void-linux/void-packages/blob/master/srcpkgs/base-system/template).

Actual guest validation found that Void's PAM configuration for `chpasswd` can accept a plain password update without producing a usable shadow hash. The engine must explicitly select SHA512 using `chpasswd -c SHA512`, feed credentials over standard input only, and verify that both root and the new user have usable hashes. A successful command exit is insufficient. See [Void's shadow package](https://github.com/void-linux/void-packages/tree/master/srcpkgs/shadow) and [chpasswd manual](https://man.voidlinux.org/chpasswd.8).

## Live ISO and tools

Official current image tested: `void-live-x86_64-20250202-base.iso`, 1,078,804,480 bytes. SHA256: `0f7439f500740f62dd18972cae448cec7d8a85032c7eb8f1bf946100d9a92161`. The checksum list was verified with minisign and the official `void-release-20250202.pub` key before the image checksum was checked. Current documentation uses **minisign**, not historical signify instructions. The ISO was downloaded unchanged; no custom ISO was produced.

Actual guest inspection found `mkfs.btrfs` and XBPS available, but **jq, sgdisk, and partprobe absent** from this base image. They must be installed into the live session using Void packages `jq`, `gptfdisk`, and `parted`. The installer fails preflight if tools are missing, before any disk changes. A working live-session network is required independently of the target's persistent network selection.

`psmisc` is also required for `fuser`, which checks for processes with open raw-device handles. Actual Void psmisc rejects the standalone `--` separator; only an independently validated absolute `/dev/` path is passed. Exit 1 with no output means no users; exit 0 blocks the disk, and any error diagnostic or other exit status blocks uncertain inspection. Checks cannot be atomic against a concurrent privileged process or hardware replacement.

Sources: [official download index](https://repo-default.voidlinux.org/live/current/), [official verification instructions](https://docs.voidlinux.org/installation/index.html#verifying-images), [official release key](https://github.com/void-linux/void-packages/blob/master/srcpkgs/void-release-keys/files/void-release-20250202.pub), [live image builder](https://github.com/void-linux/void-mklive/blob/master/mkiso.sh).

## Network and runit

DHCP uses the packaged dhcpcd service. Persistent static IPv4 uses supported `dhcpcd.conf` directives (`interface`, `static ip_address`, `static routers`, and `static domain_name_servers`). A validated physical wired interface's MAC is pinned to `voidnet0` with an installed udev rule so live-session and installed-system naming differences cannot break the selected configuration. This avoids distro-specific systemd units. User-supplied interface names and addresses must be validated before generating configuration. Services are enabled in the target's persistent `/etc/runit/runsvdir/default`, without following the live supervisor's `/var/service` symlink into its `/run`.

Sources: [Void networking](https://docs.voidlinux.org/config/network/index.html), [dhcpcd.conf manual](https://man.voidlinux.org/dhcpcd.conf.5), [Void runit services](https://docs.voidlinux.org/config/services/index.html).

DHCP configuration must preserve the packaged defaults. dhcpcd 10.3.2 explicitly requests `domain_name_servers, domain_name, domain_search` in its upstream configuration; replacing that file with a comment loses these requests. The installer now retains the defaults, adds an explicitly delimited DNS request block, and verifies the packaged `/usr/libexec/dhcpcd-hooks/20-resolv.conf` hook. The hook uses `resolvconf` when available and otherwise writes `/etc/resolv.conf` itself, so openresolv is not a mandatory dependency for this configuration. Sources: [dhcpcd 10.3.2 configuration](https://github.com/NetworkConfiguration/dhcpcd/blob/v10.3.2/src/dhcpcd.conf), [default hooks](https://github.com/NetworkConfiguration/dhcpcd/blob/v10.3.2/hooks/Makefile), [Void dhcpcd package](https://github.com/void-linux/void-packages/blob/master/srcpkgs/dhcpcd/template).

Static networking pins the selected physical Ethernet adapter by its validated MAC address to `voidnet0` using an early target udev rule. The address is read and checked again before erasing the disk; the dhcpcd stanza uses the target name. This avoids relying on live and installed udev naming being identical. Source: [udev rule ATTR and NAME syntax](https://man.voidlinux.org/udev.7).

## Preflight storage accounting

An actual 2 GiB Live-session report showed XBPS dry-run exiting 28: the private temporary root had 981 MB free, while the resolved installation needed 1158 MB. This is not the installation target. Upstream `xbps_transaction_prepare` resolves dependency/replacement/conflict/shared-library checks before computing transaction statistics with `statvfs(rootdir)`; the frontend still prints a complete dry-run plan on ENOSPC, but preserves that nonzero exit code. Download-only mode is not a suitable substitute because upstream skips conflict and shared-library checks in that mode.

The installer accepts only exit 28 with exactly the recognized space-only diagnostic and a strictly parsed nonempty six-field installation plan. Other failures remain fatal. It calculates installed sizes plus archive sizes plus 2 GiB headroom and checks this against the selected disk minus the ESP/alignment before erasure, repeating disk checks immediately before partitioning. Actual bootstrap uses the mounted disk and keeps XBPS's normal space checks. Sources: [XBPS transaction preparation](https://github.com/void-linux/xbps/blob/master/lib/transaction_prepare.c), [XBPS dry-run ENOSPC handling](https://github.com/void-linux/xbps/blob/master/bin/xbps-install/transaction.c).

## Account credentials

Actual Void Live installation testing showed that plain `chpasswd` returned zero while leaving locked or unusable root/user shadow entries. The shipped PAM configuration's password action permits the operation without updating the hash. The engine therefore uses `chpasswd -c SHA512`, passing the password on stdin and suppressing diagnostics, then independently checks that both root and user have usable SHA512 hash records. The installed-system verification repeats that check without printing hashes. This was validated by real user login, sudo password authentication and root login after reboot. Source: [Void chpasswd manual](https://man.voidlinux.org/chpasswd.8).

## Snapper

Void's Snapper template is **0.13.1_2** at research time. It explicitly disables systemd, sets global configuration under `/etc/conf.d`, ships a runit `snapperd` service, and renames the upstream cron helper to `/etc/cron.hourly/snapper`. That helper performs both timeline creation and cleanup. Use a supported cron implementation and enable its runit service plus D-Bus; do not add duplicate timers. The installed helper and global `SNAPPER_CONFIGS` entry must be verified.

Create the Snapper root configuration while `/.snapshots` is not mounted. Upstream attempts to enable a systemd timer during `create-config` when the template already has timeline creation enabled, even with Void's build configuration. Use an installer-specific copy of the packaged template with `TIMELINE_CREATE="no"`, then enable timeline creation in the resulting root config for Void's cron helper. Remove only the empty subvolume that `create-config` generated, then mount the independently created `@snapshots` there with root-only permissions. Use `snapper --no-dbus` during chroot setup because the installed system's D-Bus daemon is not running. Configuration values are quoted strings such as `TIMELINE_CREATE="yes"`. Retention is 5 hourly, 7 daily, 4 weekly, 3 monthly, 0 yearly. Create and inspect the initial snapshot.

Explicit `subvol=@` booting means changing the Btrfs default subvolume does not select a different boot root. Snapper's default-subvolume rollback workflow is not provided or advertised. No restore UI, rollback command, or grub-btrfs integration is implemented.

Snapper 0.13.1's create-config path invokes a systemctl timeline helper when its template enables TIMELINE_CREATE, even in Void's non-systemd build. To avoid this irrelevant failed command, create-config uses a private template copied from the installed default with TIMELINE_CREATE="no". The generated root configuration is then set to the requested "yes" policy for the packaged cron helper. Void's native cronie service is enabled explicitly. This behavior was verified by the second complete installation and by running the hourly helper after reboot.

Sources: [Void Snapper template](https://github.com/void-linux/void-packages/blob/master/srcpkgs/snapper/template), [Snapper hourly helper](https://github.com/openSUSE/snapper/blob/v0.13.1/scripts/snapper-hourly), [helper install path](https://github.com/openSUSE/snapper/blob/v0.13.1/scripts/Makefile.am), [default configuration](https://github.com/openSUSE/snapper/blob/v0.13.1/data/default-config), [Snapper manual](https://manpages.opensuse.org/Tumbleweed/snapper/snapper.8.en.html), [Void cron](https://docs.voidlinux.org/config/cron.html).
